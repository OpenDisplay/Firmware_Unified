# Protocol-visible changes in 3.0 (for the opendisplay-protocol owner)

Every wire- or host-visible addition made for firmware 3.0 that is **not yet in the canonical
opendisplay-protocol repo**, in one place. Each row names where the firmware defines it, its
status, and which client already implements it. Clients checked: py-opendisplay branch `v3/py`,
opendisplay.org branch `v3/website` (both local, unreleased).

Status values (since 2026-11-11 every row is final; the values live in `shared/protocol/`, and
§ "What opendisplay-protocol must receive" lists the edit):

- **provisional**: implemented and host-tested in firmware, value/placement not yet adopted by
  the protocol repo; may change.
- **awaiting maintainer decision**: implemented one way, with an open question that can change it.
- **final**: no open question; only needs writing into the protocol repo.

Nothing below has been exercised on hardware.

## What opendisplay-protocol must receive

`shared/protocol/opendisplay_protocol.h` and `opendisplay_structs.h` here are ahead of the
canonical copies by exactly these edits (each also carries a changelog bullet under
"Unreleased"). Apply them there, then sync back so the files are byte copies again.

`opendisplay_structs.h`:
- `OdPanelIcType`: `OD_PANEL_IC_M5PAPER_960X540 = 3005`.
- `SensorType`: `OD_SENSOR_TYPE_AHT20 = 7`, `OD_SENSOR_TYPE_PCF8563 = 8` (6 is the nRF
  firmware's nPM1300, still local to `targets/nordic-zephyr/src/protocol_pending.h`).
- DeviceFlags: `OD_DEVICE_FLAG_NM420_INIT (1u << 5)`.
- Config packet enum: `OD_PKT_DISPLAY_CONTROLLER = 0xB3`, with the v0 body in its @doc.
- `DriveSeqEscape`: `OD_SEQ_ESC_WINDOW = 0x0C`, `OD_SEQ_ESC_FILL = 0x0D`.
- `ActionInfoResponse`: `tables` byte appended (8 B); `rejected` doc: counts skipped entries.
- SecurityFlags: `OD_SECURITY_FLAG_NO_RESET_PATTERN (1u << 6)` (row 20, provisional), then
  drop the local copy in `shared/core/od_sec2_wire.h`.
- SecurityFlags: `OD_SECURITY_FLAG_SHOW_KEY_ON_SCREEN` @doc: "show the device key on the normal
  boot screen and in its QR (claimed devices only; SECURITY_V2 § 10.7)" instead of "future
  feature" (row 24).
- MSD status: `OD_MSD_STATUS_CLAIM_MODE` (bit 2) and `OD_MSD_STATUS_SESSION_REQUIRED` (bit 3) as
  the 3.0 names, keeping the old names as aliases (row 21); the 2.2 "dynamic all 0xFF" changelog
  line gains the 3.0 definition of "no display configured" (row 22).

`opendisplay_protocol.h`:
- CMD_READ_IDENT doc, `OD_IDENT_TARGET_ESP32` / `_NRF52840` (0x05), `OD_IDENT_FLAG_*`,
  `OD_IDENT_ESC_*` (rows 4, 5).
- § 4e `OD_ERR_DRIVE_PANEL_BUSY 0x08`; new § 4h `OD_ERR_NEEDS_MIGRATION 0x08`,
  `OD_ERR_PANEL_BUSY 0x09`; new § 4g `OD_ERR_CONFIG_WRITE_FAILED 0x00`,
  `OD_ERR_CONFIG_WRITE_BUSY 0x01`, and the CMD_CONFIG_WRITE @errors line.
- CMD_ACTION_INFO: 10-byte reply with `tables`, `rejected` semantics, BUTTON_LONG inactive,
  temperature edge and 3 C re-arm.
- CMD_POWER_OFF text: the MOSFET latch qualifies too (row 17).

Not yet edited here, and needed in the canonical repo (doc text only, no layout change):
- `opendisplay_structs.h` `FindMyCurve` / `FindMyConfig` (0x2D): no firmware computes or rotates
  an EID on-device. `OD_FINDMY_CURVE_SECP256R1` should read "reserved: no firmware advertises
  it"; the FindMyConfig @doc sentence "SECP256R1 rotates from eik+time_base on-device" should be
  dropped, and `time_base_unix` / `fmdn_k` marked unused. Network G is the static SECP160R1
  frame from `advertisement_key` with hashed-flags 0x00 (2.3.0 parity).
- `opendisplay_protocol.h` CMD_ACTION_INFO / CMD_ACTION_FIRE `@targets`: add esp32-idf
  (`OD_CAP_ACTION`, row 19).

## Not protocol changes (recorded so nobody looks for them)

- MSD status bit 3 (encryption enabled) is already canonical (`opendisplay_structs.h:1707`); 3.0
  makes every target set it from the security state and gives bits 2/3 new names (row 21).
- BG22 FMDN (network G) reuses packet 0x2D unchanged and is byte-identical on air to 2.3.0: the
  static SECP160R1 frame built from `advertisement_key` (the host computes `generate_eid(eik, 0)`),
  with the hashed-flags byte 0x00, which is what 2.3.0 sends. `fmdn_curve` 1 (SECP256R1) advertises
  nothing, as on 2.3.0; the firmware computes no EIDs and does not rotate them. The
  `FindMyCurve` / `FindMyConfig` text in `opendisplay_structs.h` still describes an on-device
  SECP256R1 rotation; see "What opendisplay-protocol must receive".
- The BG22 `SL_APPLICATION_VERSION` encoding changed to `(major<<16)|(minor<<8)|patch`; it is in
  the GBL/app properties, not on the BLE wire.
