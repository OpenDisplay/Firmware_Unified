# Protocol-visible changes in 3.0 (for the opendisplay-protocol owner)

Every wire- or host-visible addition made for firmware 3.0 that is **not yet in the canonical
opendisplay-protocol repo**, in one place. Each row names where the firmware defines it, its
status, and which client already implements it. Clients checked: py-opendisplay branch `v3/py`,
opendisplay.org branch `v3/website` (both local, unreleased).

Status values:

- **provisional**: implemented and host-tested in firmware, value/placement not yet adopted by
  the protocol repo; may change.
- **awaiting maintainer decision**: implemented one way, with an open question that can change it.
- **final**: no open question; only needs writing into the protocol repo.

Nothing below has been exercised on hardware.

## Host-visible behaviour (not new opcodes)

| # | Change | Defined at | Status | Clients |
|---|---|---|---|---|
| 10 | **A config write is stored exactly as sent** (no merge of stored drive packets). A 2.x client writing a config without 0xAE-0xB1 leaves a device that draws nothing, NACKs upload START with #3 and reports NEEDS_MIGRATION in #4; a 3.x client repairs it by writing a complete config. A damaged stored record (CRC, magic, length) is simply overwritten by the next write | `shared/core/od_config_store.c` `od_config_store_save()` (reads nothing back); every target's `saveConfig` | final | website and py-opendisplay detect NEEDS_MIGRATION via READ_IDENT and write full 3.x configs |
| 11 | **Image-store write-once slot header changed** (Nordic XIAO / Puya flash, `OD_IMGSTORE_WRITE_ONCE_HEADER=1`): CRC-32 of header bytes [0,20) at offset 20; a VALID slot with payload_len 0 or larger than the slot reads BAD on every layout. **Slots written by earlier builds read as BAD and must be re-uploaded** | `shared/core/od_imgstore.c:26,197,330`; enabled `targets/nordic-zephyr/zephyr/CMakeLists.txt:140` | final (pre-release format change) | hosts that stored images on a XIAO must re-upload (0x0047..0x004B) |
| 12 | **A partial rectangle smaller than the panel is refused (UNSUP) unless the mode's sequence has WINDOW** | `shared/core/od_display.c`; `docs/CONFIG_DRIVEN_DISPLAY.md:55-62` | final | BG22 presets have no WINDOW, so BG22 accepts only whole-panel partials |
| 13 | **0x0085 BUSY timeout / panel failure is reported as NO_CONFIG** (not a change, but host-visible and misleading) | `shared/core/od_cmd_drive.c` `drive_begin()` | awaiting maintainer decision (add a distinct OD_ERR_DRIVE_PANEL / BUSY code) | — |
| 14 | **CONFIG_WRITE (0x0041 / chunked) is NACKed while a display pass is running** (the failed-save NACK each target already sends; nothing is stored and a chunked write's reassembly is dropped). A pass reads its sequence from the stored config from begin until the tail has run, pausing for the frame; the host retries after the refresh | `shared/core/od_config_store.c` `od_config_store_save()` → `OD_CONFIG_STORE_BUSY`; held by `shared/core/od_epd_cfg.c` `set_in_pass()` and `targets/efr32bg22-slc/od_epd_shim.cpp`; `docs/CONFIG_DRIVEN_DISPLAY.md` § Limits | awaiting maintainer decision (refuse vs queue the write; whether it needs its own NACK code) | website and py-opendisplay must not write the config during an upload or a 0x0085 drive; today they would see a generic save failure |
| 15 | **No mode-sequence length cap on any target; one step cap of 128** (was 512 B / 96 steps; BG22 128 B / 64 steps). Sequences are read from storage as they run. BG22 now takes the full doubled-init sequences, so `drive_presets.json` schema_minor 2 lists no `bg22_unavailable` panels and no `alternatives` | `shared/core/od_epd.h` `OD_EPD_MAX_SEQ_STEPS`, `OD_EPD_SEQ_WINDOW`; `shared/profiles.cmake`; `panels/README.md` § Changes in minor 2 | final | website `od-v3.js` and py-opendisplay: drop the per-class `seq_max` check, use `max_steps` 128 for every class, stop offering BG22 single-init alternatives |

| 16 | **Display-mode conventions** (decided 2026-11-11): `DisplayModeHead.mode_index` is normative (packet order free, gaps allowed); first duplicate packet wins (0xB1, 0xAE per index, 0xAF per slot, 0xB2); mode 0 is always the default full refresh and the fallback for mode-unaware clients; names `fast` / `partial` reserved; a named mode that is absent or temperature-excluded falls back to mode 0; `temp_policy` SUBSTITUTE substitutes **mode 0 only** (was "lowest covering mode"); a NACK echoes the requested mode. **Mode-0 invariant**: mode 0 single-pass, `color_scheme` 0xFF or = 0x20's, i.e. the 2.x frame; a config violating it is flagged NEEDS_MIGRATION (#3/#4), not refused at write | `shared/core/od_epd_cfg.c` (`mode_entry`, `od_epd_cfg_find_usable_mode`, `od_epd_cfg_select_policy`), `shared/core/od_cfg_index.c` `od_cfg_has_drive_data`, `targets/efr32bg22-slc/od_epd_adapter.cpp`, `od_display_drive.cpp`; tests `tests/host/epd_cfg_test.c`, `legacy_upload_test.c`, `tests/panels/test_panels.py` `Mode0Invariant`; spec `docs/CONFIG_DRIVEN_DISPLAY.md` § Mode conventions | final | protocol repo: `OdDriveTempPolicy` SUBSTITUTE doc text (`opendisplay_structs.h:1312`), `DisplayModeHead` doc. Clients must write mode 0 per the invariant (the panel database already does) and read the ACK mode byte |

## Not protocol changes (recorded so nobody looks for them)

- MSD status bit 3 (encryption enabled) is already canonical (`opendisplay_structs.h:1707`); 3.0
  only makes every target set it.
- BG22 FMDN (network G) reuses packet 0x2D unchanged and is byte-identical on air to 2.3.0.
- The BG22 `SL_APPLICATION_VERSION` encoding changed to `(major<<16)|(minor<<8)|patch`; it is in
  the GBL/app properties, not on the BLE wire.
