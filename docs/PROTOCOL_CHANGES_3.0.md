# Protocol-visible changes in 3.0 (for the opendisplay-protocol owner)

Every wire- or host-visible addition made for firmware 3.0 that is **not yet in the canonical
opendisplay-protocol repo**, in one place. Each row names where the firmware defines it, its
status, and which client already implements it. Clients checked: py-opendisplay branch `v3/py`,
opendisplay.org branch `v3/website` (both local, unreleased).

Status values:

- **provisional**: implemented and host-tested in firmware, value/placement not yet adopted by
  the protocol repo; may change.
- **awaiting maintainer decision**: implemented one way, with an open question that can change it.
- **final**: no open question; only needs writing into the protocol repo.

Nothing below has been exercised on hardware.

## Host-visible behaviour (not new opcodes)

| # | Change | Defined at | Status | Clients |
|---|---|---|---|---|
| 10 | **Config-write carry ("guard")**: a config write with no 0x80+ packet keeps the stored 0xAE-0xB1 drive packets (merged in before the CRC tail). Too big after merge → refused TOO_BIG, nothing written | `shared/core/od_config_carry.c`, `.h`; called from every target's saveConfig (ESP32 in its own commit 2175ce3) | awaiting maintainer decision (merge vs refuse; whether 0xB2 is carried too — today it is NOT, KNOWN_BUG CARRY-ACTIONS) | py-opendisplay and website write full 3.x configs (with drive packets), so they never trigger it |
| 11 | **Zero-length 0xB1 as an explicit drive-data wipe**: `[n][B1][00 00]`. Implemented as "any 0x80+ packet means the config is stored as sent" (`shared/core/od_config_carry.c:29-30`), so ANY zero-length 0x80+ packet wipes, and the wipe is global (names no instance) | `shared/core/od_config_carry.c:29`, `shared/core/od_config_carry.h:10,39`; `docs/CONFIG_DRIVEN_DISPLAY.md:124-126` | awaiting maintainer decision (only a zero-length 0xB1, or any zero-length 0x80+?) | none |
| 12 | **Config-store errors `OD_CONFIG_STORE_IO` / `OD_CONFIG_STORE_UNSAFE_CARRY`**: a 2.x write onto a device whose stored record cannot be read or fails magic/length/CRC/walk is refused with nothing written (fail-closed). Firmware-internal enum; on the wire the config write NACKs exactly as any other refused write | `shared/core/od_config_store.h:65,69` | awaiting maintainer decision (fail closed vs overwrite a corrupt record) | n/a (no distinct wire code) |
| 13 | **Image-store write-once slot header changed** (Nordic XIAO / Puya flash, `OD_IMGSTORE_WRITE_ONCE_HEADER=1`): CRC-32 of header bytes [0,20) at offset 20; a VALID slot with payload_len 0 or larger than the slot reads BAD on every layout. **Slots written by earlier builds read as BAD and must be re-uploaded** | `shared/core/od_imgstore.c:26,197,330`; enabled `targets/nordic-zephyr/zephyr/CMakeLists.txt:140` | final (pre-release format change) | hosts that stored images on a XIAO must re-upload (0x0047..0x004B) |
| 14 | **A partial rectangle smaller than the panel is refused (UNSUP) unless the mode's sequence has WINDOW** | `shared/core/od_display.c`; `docs/CONFIG_DRIVEN_DISPLAY.md:55-62` | final | BG22 presets have no WINDOW, so BG22 accepts only whole-panel partials |
| 15 | **0x0085 BUSY timeout / panel failure is reported as NO_CONFIG** (not a change, but host-visible and misleading) | `shared/core/od_cmd_drive.c` `drive_begin()` | awaiting maintainer decision (add a distinct OD_ERR_DRIVE_PANEL / BUSY code) | — |

## Not protocol changes (recorded so nobody looks for them)

- MSD status bit 3 (encryption enabled) is already canonical (`opendisplay_structs.h:1707`); 3.0
  only makes every target set it.
- BG22 FMDN (network G) reuses packet 0x2D unchanged and is byte-identical on air to 2.3.0.
- The BG22 `SL_APPLICATION_VERSION` encoding changed to `(major<<16)|(minor<<8)|patch`; it is in
  the GBL/app properties, not on the BLE wire.
