## 1. BG22 action system and the temperature trigger (OD58FFC4)

Commits `670232a`, `f3115d6`, `1d30361`, `4c76b7b`, `803693f`, `877124b`.

The trigger table (`0xB2`) replaced the old LED/NFC flag bits. Verified on OD58FFC4:
closed-loop temperature trigger fires on a real crossing.

**Two defects found, one fixed, one still open.**

- *Fixed:* `shared/` held two CRC-32 implementations and read an ambient clock (`f3115d6`).
- *Open:* **temperature triggers chatter** — one crossing produced four fires, because there is
  no hysteresis/deadband. Recorded in `docs/FOLLOWUPS.md`.
- *Open:* **BUTTON_PRESS and NFC_FIELD triggers are unexercised** on any board.

**Trap worth remembering:** `interrogate → append → write_config` stacked **four** `0xB2` action
tables into one config. `od_cfg_find` resolves by *first match*, so the oldest table won and the
newest was silently dead. The host-side fix is to filter before appending:

```python
[p for p in cfg.unknown_ex_packets if p[1] != 0xB2]
```

Drive packets (`0xAE`–`0xB1`) need the *other* treatment — py-opendisplay models them as
`display_modes` / `display_luts` / `display_panels`, not as `unknown_ex_packets`, so appending
there silently duplicates too. Clear those fields instead.

## 2. nRF52840 — USB-only install, then BLE OTA end to end

Commits `ab4f782`, `625c95d`, `e66d9cc`, `640fe40`, `5aa948a`, `fd7f202`, `190090a`,
`ee1e783`, `7a5fe9d`, `5048711`.

Constraint that framed everything: **the initial install can only go over USB**, and nRF52840
has no ROM USB bootloader. EN04/EN05 ship the Adafruit bootloader at `0xF4000` + MBR + s140.

**The move that unblocked it: erase the SoftDevice.** Zephyr/NCS uses the SoftDevice *Controller*
library (SDC), not the legacy s140 blob, so the 152 kB s140 is dead weight. Removing it freed
enough flash for a genuine dual-slot MCUboot layout.

Final static map — `targets/nordic-zephyr/zephyr/pm_static_nrf52840_mcuboot.yml`:

| Region | Start | Size |
|---|---|---|
| `mbr` | `0x0` | `0x1000` |
| `mcuboot` | `0x1000` | `0xC000` |
| *(gap → primary)* | `0xD000` | 440 kB |
| `mcuboot_secondary` | `0x7B000` | `0x6E000` |
| `settings_storage` | `0xE9000` | `0xB000` |
| `adafruit_bootloader` | `0xF4000` | `0xC000` |

**Verified on hardware: upload, swap, and rollback.** Not a build claim.

Other decisions: MCUboot's boot-mode request goes in **GPREGRET2** with the watchdog breadcrumb
moved to RAM (`fd7f202`) — GPREGRET1 stays for `enter_adafruit_dfu()`'s `0x4E`. The image-confirm
guard is `CONFIG_MCUBOOT_IMG_MANAGER`, not `CONFIG_BOOTLOADER_MCUBOOT` (`625c95d`); those are
different symbols and the wrong one compiles silently.

**Release blockers:** MCUboot's **published debug key must not ship**, and the fleet SoftDevice
migration is a **per-device USB visit** — there is no remote path to it.

**Process failure worth not repeating:** three successive boot-mode relocations with *no
discriminating diagnostic* between them, so each attempt's failure looked like the last.
`190090a` exists only to report the boot-mode request at boot. Add the diagnostic first.

## 4. PPK2 power benchmark — stock Silabs vs universal (ODBEEBA6)

2.9″ BWRY, 168×384, 3.0 V via PPK2 source meter.

| Phase | Stock Silabs | Universal | Δ |
|---|---|---|---|
| Idle (advertising) | 20.7 µA | **19.6 µA** | −5% |
| Connect handshake | 33.0 µA / 16.1 s | 31.7 µA / 16.8 s | −4% |
| Connected idle | 87.1 µA | **91.3 µA** | +5% |
| Upload + refresh | 20.8 s · 286.80 mJ · 26.56 µAh | **21.5 s · 295.24 mJ · 27.34 µAh** | +3% |
| Post-refresh settle | 85.3 µA | 83.3 µA | −2% |

**Conclusion: parity within ±5% on every phase — no regression from the migration.**

One non-noise difference: upload **peak** fell 29.3 → 19.4 mA while the mean held (4589 →
4576 µA) — same work, flatter profile, likely the preset's `0xAF` LUT versus the stock built-in
waveform. Caveat: 19.4 mA is also the advertising-burst peak in every other phase, so the refresh
peak may simply be hidden under the radio peak.

**Caveat attached to all of these numbers: no camera covers the PPK2 bench.** Uploads are
evidenced by BLE completion plus the current signature only. The rig harness header warns that a
textbook current trace can accompany a garbage render.

### Measurement traps that cost real time

1. **PPK2 serial port.** `list_devices()[0]` is the *control* interface on this machine, not the
   data one. It does not error — it returns ~12 samples of nonsense (43 A mean). Pin
   `/dev/ttyACM1`. **`hil_rig/harness/ppk2.py` still has this bug.**
2. **PPK2 drops DUT power when the controlling serial connection closes.** The user caught this
   from the glass: "the power is turned off after a bit somehow". Hold the port open in one
   long-lived process.
3. **Idle measured 3× too high (62.9 µA)** because a fixed 25 s wait straddled the end of boot —
   the device does not advertise until t+30 s. Gate on *actually seeing it advertise*, then settle
   45 s. Cross-check that supports 20.7 µA: post-refresh settle (85.3 µA) and connected idle
   (87.1 µA) are both still-connected states and agree within 2%.

## 5. 16 colours — diagnosed as a migration regression, not a missing feature

The stock Silabs firmware did 16 colours **host-side via `CMD_SPI_RAW`**. The universal firmware
*declares* that opcode but **does not route it**. Separately, the `colour16` mode is unreachable
because `mode_index` is hardcoded `0u`.

So this is not "a feature we never built" — it is a capability the migration dropped. The
replacement path is the config-driven drive opcode in § 6.

Also settled: **`bwry16` is a MODE, not a colour scheme.** Scheme 10 belongs on the `0xAE` mode
packet and must never be written into DisplayConfig `0x20` — unknown schemes degrade to
greyscale/mono *silently*.

## 6. `CMD_DRIVE_WRITE_START` (0x0085) — wire half ported

Commit `fcbc91f`. Ported from my own `Firmware_Silabs` `feat/od-epd-driver`
(`opendisplay_pipe.c:724`, `handle_drive_write_start`).

Why the opcode exists: the mode must be known **at START**, because the driver uploads the
waveform as part of the init sequence, *before* the frame. `0x0072` END carries a `refresh` byte
but it arrives after the pixels are already in the panel. And 16-colour BWRY needs three passes
whose pixel codes genuinely differ per pass, which `0x0070` cannot express.

| File | Role |
|---|---|
| `shared/core/od_caps.h` | `OD_CAP_DRIVE_WRITE`, default **0** |
| `shared/core/od_dispatch_ops.h` | `OD_DISPATCH_DRIVE_ROWS`, one row, 1 reply unit |
| `shared/core/od_cmd_app.h` | hook declaration under the cap |
| `targets/efr32bg22-slc/od_cmd_drive.c` | wire half: validation, reserved-byte rejection, ACK/NACK |
| `targets/efr32bg22-slc/od_display_drive.{h,cpp}` | panel seam, answers `OD_ERR_DRIVE_UNSUPPORTED` |
| `tests/host/drive_display_test_stub.c` | fakes **only** the seam, so the real wire half is tested |

Answering `OD_ERR_DRIVE_UNSUPPORTED` rather than leaving the opcode unrouted is deliberate:
"I know this opcode and cannot do it yet" ≠ "I have never heard of this opcode", and *unknown* is
wire-visible (`od_frame_policy` gives an unrecognised opcode no activity stamp).

**Two bugs the compiler caught in my own port**, both from transcribing an adjacent file instead
of reading the spec:

- `RESP_ACK_B` is a **locally defined imgstore symbol equal to `0x01`** in `od_cmd_flash.c`. The
  canonical ACK for `0x0085` opens with `RESP_ACK` = **`0x00`**. Would have been a wrong first
  byte on every successful reply.
- `#include "od_cmd_reply.h"` exists on esp32 and nordic but **not** on silabs, which uses shared
  `od_reply.h` directly.

**Verified:** host suite 80/82, with the real `od_cmd_drive.c` linked into both silabs executables
against the 2 KiB/three-slot ABI; clean BG22 build; both new files cross-compile for Cortex-M33
under `-Wall -Wextra -Werror`; the `.cpp` compiles to an **empty object** when the cap is off.
Cost: **256 B** of flash in the real link.

### Still to do (step 3 and 4)

1. **Pass count from the mode.** `opendisplay_display.cpp` hardcodes `is_gray4 ? 2 : 1`;
   `OdEpdAdapter::passCount()` exists and is **called by nothing**.
2. **Plane N routed to pass N.** Planes are currently *derived locally* by bit-splitting one
   buffer (`make_gray4_plane_row`). 16 colours needs three frames whose codes differ —
   `palette[cell][pass]` — **streamed from the host**, because the palette is panel-specific and
   entries 2/3 still have an open yellow/red conflict. It must not be frozen into firmware.
3. **`temp_policy` enforcement** between mode selection and the first pass: REJECT / SUBSTITUTE
   (answer with a *different*, temperature-legal mode) / ADVISORY, plus `drive_temp_c()` /
   `mode_temp_ok()` helpers.
